> 상태: **P0 확정**. 기준 코드 = `docs/v3-growth-revision` f174dce (main c13d9b2 v0.1.22 + 기획·시범 아트).
> 기획 원문: [growth-plan.md](growth-plan.md) · 화면: [ui-contract.md](ui-contract.md) · 수급표(자동 생성): [supply-table.md](supply-table.md).

## 1. 보존하는 기존 기준값 (코드에서 읽은 값)

| 항목 | 값 | 출처 | V3에서 |
|---|---|---|---|
| 영웅 레벨 공격력 | (Lv−1) × **+4%** (bp 400) — 공격력% 합에 더함 | `game.json towerLevel.atkPerLevel`, `Aura.towerBonus` | 그대로 |
| 특색 수치 | `[Lv1, Lv15]` 정수 보간 `a + trunc((b−a)(lv−1)/14)` | `abilities/params.ts lerpLevel` | 그대로 (마일스톤은 별도 항) |
| 영웅 레벨 상한 | 15 | `progression.json heroes.maxLevel` | 그대로 |
| 영웅 레벨업 비용 | 카드 `cards[n−1]×등급%`(올림) + 불꽃 `flame[n−1]×등급%`(내림) | `progress.levelUpCost` | 그대로 |
| 판 정산 | 경험치 10/웨이브 + 50/보스, 골드 20/웨이브 + 100/보스, 불꽃 2/웨이브 + 10/보스, 카드 `cardsByStage`, 리미티드 조각 1/보스 | `progression.json matchRewards` | 그대로 (V3 보상은 그 **아래에 더함**) |
| 시작 자금 | 1,000원 | `game.json match.startGold` | 그대로 (유물만 더함) |
| 이자 | 보유 100원마다 10원, 1회 최대 10,000원 | `game.json interest` | 그대로 (유물만 더함) |
| 일꾼 | 300원, 최대 10명, 5초마다 1명당 5원 | `game.json worker` | 그대로 (유물만 더함) |
| 도박 | 표 기대 지급률 128.5% + 잭팟 게이지 | `game.json gamble` | 그대로 (유물은 꽝 비용 환급만) |
| 공속 상한 | 기본의 ×5, 초당 15회 | `game.json combat` | 그대로 |
| 치명 확률 상한·관통 상한 | 100% · 90% | `game.json combat` | 그대로 |
| 일일 퀘스트 | 기기 날짜 자정 초기화, 4개 + 모두 완료 보너스 | `progression.json quests.daily` | **그대로 유지** (V3 신규만 진행도 기반) |
| 판 밖 저장 | `rtd.progress` 형식 v2, 모르는 필드는 보존 | `progress.parseProgress` | v2 유지 (아래 4장) |
| sim 버전 | `SIM_VERSION = 2` | `src/sim/version.ts` | P1·P2에서 각각 +1 |

보존 약속 (P1~P3 테스트로 확인):
1. 같은 영웅·계정Lv·판 입력·배치·시드에서 기존 공격력·공속·사거리·치명·관통·제어 지속·발동 확률이 **낮아지지 않는다**. 65종 각각(평균 아님).
2. 유물·마일스톤이 없는 판(Lv1~2 영웅, 유물 0)은 지금과 **같은 결과**(리플레이 해시 동일)를 낸다.
3. 기존 저장의 잔고·카드·레벨·해방·설정·기록은 읽고 쓴 뒤에도 같다. 새 필드는 없으면 기본값.
4. 기존 경제 수치(이자·도박·일꾼·소환·판 보상)를 깎지 않는다. 경제 유물은 자기 상한·후보값으로만 조정한다.

## 2. 효과 합성 순서·상한 (P1·P2 sim)

모든 값은 bp(1/10000) 정수, 곱한 뒤 내림. 한 타워의 최종 보정은 `Aura.towerBonus` 한 곳에서 만든다.

| 단계 | 합성 | 상한 |
|---|---|---|
| 공격력% | **합연산**: 오라 + 영웅 레벨 (Lv−1)×4% + 등급 강화 + 판 내 강화·카드 + **마일스톤 공격력** + **유물 공격력**(숫돌·피해 유형·금화 망치) | 금화 망치만 자기 상한 +30%. 전체 하한 −100% |
| 공속% | 합연산: 오라 + 전군 가속 + 특색 + **마일스톤 공속** + **유물 공속**(바람개비) | 기존 상한(기본 ×5·초당 15회) |
| 치명 확률 | 합연산: 기본 + 판 내 + **마일스톤 치명** | 기존 100% |
| 보스 피해 | 곱: (1 + 판 내 보스%) × 특색 배율 × (1 + **사냥꾼 표식**) | 없음 (후보값 Lv10 +15.2%) |
| 오라(지원 영웅) | 오라 값 × (1 + **마일스톤 오라%**) 내림 | 같은 종류 중첩 없음 규칙 그대로 |
| 제어 시간 | 지속 틱 × (1 + 마일스톤 제어% + **서리 결정**) 내림 → 기존 보스·저항 배율 | 기존 둔화 최대·면역 규칙 |
| 경제 | 이자 상한 += 저금통, 이자율 += 1%p(고정) · 시작 자금 += 지갑 · 일꾼 1명당 수입 += 장갑 · 꽝 환급 = 그 시도 비용 × 쿠키% (1회, 환급은 잭팟·재시도를 부르지 않음) | 저금통 Lv10 상한 +6,500 |
| 누수 | 무한 몹 한도 += 울타리, 캠페인 목숨 += 울타리 | Lv5 +5 |

마일스톤은 **판 입력(영웅 레벨)에서 정해지는 값**이라 판 상태·해시에 들어가지 않고, 유물은 **판 입력 `relics`**(플레이어별 유물 id → Lv)로 리플레이·판 저장에 기록한다.

## 4. 진행도 규칙과 단일 지급 장부

### 4.1 정의

- **완료 웨이브** = 끝난 웨이브 수. 승리(캠페인 마지막 단계 생존) = 도달 단계, 그 밖(패배·포기·업데이트로 버린 판) = 도달 단계 − 1. 진 웨이브는 완료가 아니다.
- **유효 전투** = 치트 없는 판(`dev`·`debugUsed` 아님) + 완료 웨이브 ≥ 10. 무한·캠페인 모두.
- 보급·성장 선택·도장·패스 계산은 `src/meta/v3/explore.ts` 한 곳. 화면은 이 결과만 그린다(자격을 따로 계산하지 않는다).
- 날짜·시계·시간대는 어떤 V3 값에도 들어가지 않는다. 기존 일일 퀘스트만 기기 날짜를 쓴다.

### 4.2 경계 예시 (테스트 `v3-p0-explore`)

| 입력 | 결과 |
|---|---|
| 완료 9 | 기존 정산만. 도장·보급·나머지 변화 없음 |
| 완료 10 | 도장 1 · 보급 1 · 나머지 0 |
| 완료 27 | 도장 1 · 보급 2 · 나머지 7 |
| 이어서 완료 13 | 7 + 13 = 20 → 보급 2 · 나머지 0 |
| 완료 80 | 보급 8 · 성장 선택 2 (나머지 2) |
| 도장 27 → 28 | 1회차 완성. 29번째 유효 전투는 2회차 1칸, 1회차 미수령은 그대로 |
| 패스 49 → 50칸 | 시즌 완료. 넘친 웨이브는 다음 시즌으로 이월, 다음 시즌은 미수령을 받은 뒤 직접 넘김 |

### 4.3 장부 (중복 지급 방지)

1. **판 장부** = 기존 `rewardedRuns`(runId, 최근 20판). `settleMatch`가 runId를 먼저 확인하고, 처음일 때만 **기존 정산 + V3 탐험 진행**을 한 번에 더한다. 패배 화면·이어 하기·업데이트로 버린 판(`settleAbandonedRun`)이 모두 이 한 함수를 지난다 → 같은 runId를 다시 정산하면 V3 보상도 0.
2. **보급 지급**: P2에서는 정산 때 보급 수만큼 열쇠·목표 조각을 바로 준다(정산 화면 '탐험 보상'). P3에서는 같은 보급 수를 **보급 상자**로 쌓고, 상자를 열 때 같은 보상을 준다. 두 경로는 같은 빌드에 함께 있지 않다(P3가 P2 직접 지급을 대체) → 같은 보급이 두 번 지급되지 않는다.
3. **1회 지급 장부** `v3.granted` = 지급ID 목록 (runId와 별개): 첫 유물 선택권 `first-relic`, 첫 영웅 선택권 `first-hero`, 비밀 코드 `code:<id>`, 성장 꾸러미 `pkg:<id>`, 황금 트랙 `pass:<시즌>:golden`. 이미 있으면 다시 주지 않는다.
4. 한계 (주장하지 않는 것): 기기 저장을 통째로 예전 백업으로 되돌리는 오프라인 조작은 막지 않는다(판 장부도 같이 되돌아가므로). 서버가 없는 오프라인 게임의 한계로 문서화한다.

### 4.4 기존 계정 처리

- 신규 도장·패스·보급은 **P2/P3 업데이트 이후 유효 전투부터** 센다. 과거 판 수를 환산하지 않는다.
- 이미 Lv3/6/9/12/15인 영웅은 마일스톤이 즉시 적용(판 입력이 레벨에서 바로 계산 — 구매·수령 버튼 없음).
- 첫 유물 선택권·첫 영웅 선택권은 기존 계정에도 1회. 고른 영웅을 이미 가졌으면 카드로 바꿔 준다(사라지지 않음).
- 성장 꾸러미는 계정 레벨이 이미 넘었으면 바로 열린다.
- 저장 형식은 **v2 유지**: 새 필드는 모두 추가·기본값이고 기존 필드의 뜻은 바뀌지 않는다. 예전 앱은 모르는 최상위 필드(`v3`)를 지우지 않고 들고 다닌다(M4 규칙).

## 5. SIM_VERSION·진행 중 판

- P0: sim·게임 데이터 변경 없음 → `SIM_VERSION` 2, 데이터 지문 그대로 (progression.json은 지문 밖).
- P1: 마일스톤이 같은 입력에서 다른 결과를 냄 → **3**. P2: 판 입력 `relics`·경제 규칙 → **4**.
- 버전이 달라진 진행 중 판은 기존 정책대로 **runId로 한 번 정산한 뒤** 버린다(V3 탐험 진행도 같은 정산에서 한 번). 계정·재화는 유지.
- 리플레이: 영웅 Lv1~2·유물 0인 기존 리플레이는 해시가 같아야 한다. 레벨이 3 이상인 리플레이만 다시 만든다.

## 6. 측정 기준

- 무료 트랙 수급표: [supply-table.md](supply-table.md) — 표준 10웨이브 완료 전투 기준 성장 선택 3판마다, 주력 유물 p50 55~58판(교환 없음), 영웅 꾸러미로 목표 영웅 Lv15 42판.
- P2 sim 비교: `tests/integration/v3-relic-bots.test.ts`(P2) — 같은 시드·배치 봇으로 유물 없음/전투형/경제형/혼합형의 도달 웨이브·보스 시간·소환·보유금을 기록한다. 경제형이 전투형을 일관되게 압도하면 **신규 유물 후보값만** 조정한다.
- 실제 정산 코드 재측정: P2·P3 테스트가 `settleMatch`를 표준 전투로 반복해 수급표와 같은 정책의 판 수를 다시 잰다.
